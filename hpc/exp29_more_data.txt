# exp29 -- is the deliverable DATA-LIMITED at its own size? 12 jobs, GPU.
#
#     sh hpc/submit.sh hpc/exp29_more_data.txt data29 hpc/job_sweep_gpu.sh
#
# ONLY AFTER (1) hpc/job_gen_famZ.sh has written data/famZ_W40.npz -- submit.sh refuses a
# missing or truncated dataset anyway -- and (2) hpc/job_gpu_smoke.sh has come back with
# an s/epoch that passes the rule under QUEUE below.
#
# WHY. F55 ("data saturates near n=5000") was measured at L2_w64, where famO's val/train
# gap is 1.52. The gap grows with capacity on the limited families and the deliverable
# sits far out on that curve:
#
#     val_th / train_th     L2_w64   L3_w128   L4_w128
#     famO                   1.52     3.67      4.08      (4.1 over exp28's 8 seeds)
#     famN                   2.01     4.84      3.23
#     famR (unlimited)       1.45     1.81      1.85
#
# F55 does not cover the deliverable, and F22 showed that closing a gap with data is real
# here (n=1000 -> 5000: gap 2.60 -> 1.45, val_th 1.83x). This is the one lever left with
# measured evidence behind it.
#
# DESIGN. Two arms, 12 jobs, all L3_w128 with gains, identical flags to exp28's baseline:
#
#     famZ n=10000, GPU   seeds 0-7    THE QUESTION: twice the data
#     famO n=5000,  GPU   seeds 8-11   HARDWARE CONTROL
#
# The control exists because this changes TWO things at once -- the data and the hardware
# (the 8 baseline seeds ran on milan CPUs, these run on a GPU) -- which is exactly what
# F68/F69 were built to avoid. A GPU run is a fresh draw (other kernels, another randperm
# stream), and 8-vs-16 CPU cores already moved one seed by 1.16x, so the GPU gets its own
# check: if the control lands inside the CPU baseline's seed range, any famZ difference
# is the data. SEEDS 8-11, NOT 0-3: sweep.py has no --runs_dir, so famO seeds 0-7 would
# overwrite existing checkpoints in runs/ -- seed 0 IS the deliverable.
#
# --epochs 1200 --patience 40 unchanged, so the protocol matches the baseline. One epoch is
# one pass over the data, so famZ takes twice the gradient steps per epoch. F55's famG ran
# into the cap at 2x data; a famZ seed that hits 1200 is under-trained, which biases AGAINST
# more data. Check epochs_run before reading anything.
#
# QUEUE -- decided by the smoke test, not assumed. famZ at the 1200-epoch worst case costs
# 2 x 1200 x (smoke-test s/epoch at n=5000). job_sweep_gpu.sh asks gpul40s for 47 h:
#     smoke s/epoch < ~70     gpul40s as written
#     ~70 to ~105             change job_sweep_gpu.sh to  -q gpua100  and  -W 71:00
#     > ~105                  the GPU does not make n=10000 affordable at L3_w128. STOP and
#                             rethink before submitting; milan's 47 h fits neither.
#
# HOW TO READ IT. famZ and famO have different validation splits, so their own-split
# rollout_full_rms is NOT a common test (F59/F61). Every run of each family is unseen by
# the other family's models, so both splits are fair held-out sets for both: score all
# 20 checkpoints (8 CPU baseline, 4 GPU control, 8 famZ) on famO's val split AND famZ's,
# and report both. That needs a small cross-scoring script, written when results land.
# Report RMS and worst case, as always.
#
# PRE-REGISTERED, before looking. The last two predictions here failed (F69's exp24, F72).
#   famZ beats the baseline by >= 1.2x on deployed RMS on BOTH test splits, and its
#   val/train gap falls to <= ~2.5. If the gain is < 1.1x, the deliverable is not
#   data-limited at this size either: the gap is where this setup sits, as F55 concluded
#   for the small model, and the architecture is done -- write-up time.
#   The GPU control lands inside the CPU baseline's seed range (RMS 7.62-8.93e-4).
