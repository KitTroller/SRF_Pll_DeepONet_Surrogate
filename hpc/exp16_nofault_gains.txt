# Two questions, one array, 16 jobs. Both are about SHRINKING what the model has to
# cover so the fixed budget buys more accuracy where Rahul actually runs.
#
#   Q1  FAULTS.  His supervisor says the co-simulation's own network solver produces the
#       sags and jumps, so we do not have to. Today 50% of our runs carry a fault
#       (`disturbances.fraction: 0.5`). Turning them off does not change n_runs, so the
#       clean regime gets sampled TWICE as densely for the same compute.
#
#   Q2  GAIN BOX.  F57 measured the price of making Kp and Ki inputs at 3.5x deployed
#       angle error. graphs/rahul/03 shows that price is not uniform across the box.
#       If we ask Rahul for a smaller range, how much of the 3.5x do we get back?
#
# FOUR ARMS, and they are laid out so each comparison moves ONE thing:
#
#   famL   no faults, WIDE gains (Kp 10-50, Ki 100-600)   W=40, W=20
#   famM   no faults, TRIMMED gains (Kp 18-45, Ki 180-520) W=40, W=20
#
#     famL vs famJ (exp14, faults ON, same wide box, same omega, same n_runs)  ->  Q1
#     famM vs famL (same everything except the box)                            ->  Q2
#
# Both are WIDE omega (+/-20), matching famJ. Not narrow: F61 retracted the narrow-omega
# win once the arms were scored on a COMMON test set instead of each on its own
# validation split, and famJ is the wide-omega arm, so wide is what keeps Q1 one-factor.
#
# THE BOX I ACTUALLY PICKED, AND WHY IT IS NOT THE ONE THE ZETA STORY SUGGESTS.
# "Cut the underdamped corner" would mean raising Kp_lo and lowering Ki_hi, e.g.
# Kp 20-50 / Ki 100-400 -> zeta >= 0.5. Read graphs/rahul/03 (left panel) before doing
# that, because the measured error does not follow zeta:
#
#     Ki=100 row:  2.4e-3 at Kp=18 (zeta 0.90, WELL damped) and 1.8e-3 at Kp=50
#                  (zeta 2.50, heavily OVERdamped) -- both bad
#     Kp=10 col:   worst column overall, and it spans zeta 0.20 to 0.50
#     sweet spot:  Kp 25-41, Ki 200-500 -> 6.7e-4 to 8.4e-4
#
# So the bad regions are the SLOW loop (low Ki, small wn) and the LOW-GAIN column, plus
# the overdamped corner -- not "low zeta". A zeta>=0.5 box would keep the worst row we
# have (Ki=100) and throw away the good high-Ki region. Kp 18-45 / Ki 180-520 trims the
# four measured-bad edges instead, is the same 46% of the original volume, and leaves
# their tuning (25/300) comfortably interior at 26% / 35% of each range.
#
#   trimmed box:  zeta 0.395 - 1.68,  wn 13.4 - 22.8 rad/s
#   original:     zeta 0.204 - 2.50,  wn 10.0 - 24.5 rad/s
#
# CAVEAT ON THAT READING, state it before anyone leans on it. The heatmap metric is an
# ABSOLUTE theta RMS. At Ki=100 the loop period is 0.63 s, longer than the 0.5 s window,
# so those runs are still in transient at the end and |theta| itself is larger. The bad
# edges may be where the answer is big rather than where the model is relatively worse.
# This does NOT touch the famM-vs-famL verdict, which is a common-test comparison where
# that confound cancels -- it only means "which cells are hard" is not yet settled.
#
# WHAT REMOVING FAULTS COSTS, and it is a real risk, not a formality. The model will have
# NEVER seen a sag or a phase jump. In the co-simulation those waveforms still arrive at
# our branch input as Va,Vb,Vc -- they come from his solver, but we still have to read
# them. famL/famM are therefore extrapolating during every fault. That has to be measured,
# not assumed away, and the measurement is cheap because famJ's faulted windows are
# already a labelled test set (`fault_kind != 0`).
#
# WHAT TO RUN AFTERWARDS -- the comparisons are NOT the per-family val numbers.
# Scoring each model on its own family's validation split is exactly the mistake that
# produced F59 and had to be retracted in F61, five times this week in total. Use the
# common-test harness, `rollout_err` in src/gain_sensitivity.py:
#
#   Q2  score famM and famL on the SAME cells, all inside the TRIMMED box. famL is
#       in-domain there too, so this is fair to both. If famM is not clearly better
#       inside its own box, shrinking the range is not worth asking Rahul for.
#   Q1  score famL and famJ on the same CLEAN cells  ->  what the density buys.
#       Then score both on famJ's FAULTED windows    ->  what it costs.
#       Report both numbers together or the answer is dishonest.
#
# PRE-REGISTERED PREDICTIONS, so the result cannot be rationalised afterwards:
#   Q1  clean accuracy improves, but by less than sqrt(2); faulted accuracy degrades a
#       lot, plausibly >5x, because it is pure extrapolation.
#   Q2  famM beats famL inside the trimmed box by roughly 1.3-1.8x. Not the full 3.5x --
#       that is the price of gains-as-inputs at all, and halving the box cannot refund it.
#   If Q2 comes back flat, the honest conclusion is that the gain-input cost is about
#       having two extra input dimensions, not about how wide they are, and we should
#       stop asking Rahul to constrain his tuning.
#
# REPRODUCIBLE, and this is the first batch that is. Both families are generated with
# --lhs_seed 11. Because `create_disturbance_space` returns before touching the RNG when
# faults are off, famL and famM get IDENTICAL initial conditions, IDENTICAL grid
# waveforms and IDENTICAL gain u-draws -- only the affine map onto (Kp,Ki) differs.
# Verified on an 8-run pair: Va, Vb, Vc, lhs_samples, run_id, segment_id all bit-equal;
# only kp, ki and the resulting trajectories move. Q2 is therefore PAIRED, which is why
# 4 seeds per arm is enough here.
#
# GENERATE FIRST (submit.sh refuses to submit if a --dataset is missing):
#   .venv/bin/python hpc/generate_family.py --stem famL --W 20 40 --n_runs 5000 \
#       --gains --no_faults --lhs_seed 11
#   .venv/bin/python hpc/generate_family.py --stem famM --W 20 40 --n_runs 5000 \
#       --gains --no_faults --lhs_seed 11 --kp_range 18 45 --ki_range 180 520
#
# EPOCHS 1200 ON EVERY ARM, W=40 included, so the cap stops being a hidden hyperparameter.
# `patience` 40 is what should end a run; a ceiling that ends it instead turns an accuracy
# comparison into an epochs comparison. That already happened once: W=20 hit the old 800
# cap every single time, and when it was raised the W=20 penalty fell from 2.3x to 1.88x
# -- a third of the "windowing penalty" was the cap. A cap a run never reaches costs
# nothing, so there is no reason to keep one low enough to bind.
#
# THE BASELINE IS ALREADY FAIR, checked rather than assumed:
#
#   grep -ho '"epochs_run": [0-9]*' Hyperparameter_sweep/sweeps_famJ_W20/*.json | sort -u
#   -> 1024, 1047, 1097, 1099
#
# Four DIFFERENT values, so all four early-stopped on patience under a cap of at least
# 1100 (the cluster's exp14 was at 1200; the copy in this repo still reads 800). famJ_W20
# therefore needs no re-run and famJ_W40 needs no check -- matching 1200 here makes the
# Q1 comparison at both window lengths an accuracy comparison and nothing else.
#
# Cost: a W=40 job that actually wants all 1200 epochs is ~9 h at the measured ~28 s per
# epoch, inside job_sweep.sh's 24 h wall time with room to spare.
